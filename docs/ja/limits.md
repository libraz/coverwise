# 入力上限

モデルが宣言できる内容は 7 つの上限で制限され、どのサーフェスも同じ 7 つを適用します。コマンドライン、Python パッケージ、WebAssembly ビルド、ピュア TypeScript 移植、C++ ライブラリのいずれも同じです。これらは coverwise が受理する範囲を定めるものであって、チューニングの設定ではありません。1 つの判断にかけてよい計算量を制限する内部予算は、ここには載せていません。その値は将来変わる可能性があります。上限の超過は、その上限を名指しするメッセージを伴う拒否になります。結果が切り詰められたり、途中まで返ってきたりすることはありません。

## 宣言済みの上限

| 上限 | 値 |
|------|-----|
| モデル 1 つが宣言できるパラメータ数 | 1,024 |
| パラメータ 1 つが宣言できる値の個数 | 16,384 |
| `tests`・`seeds`・`existing` 配列の行数 | 100,000 |
| モデル 1 つの制約式の個数 | 256 |
| 単一の入力文字列の UTF-8 バイト数 | 65,536 (64 KiB) |
| 入力 1 件の全文字列を合計した UTF-8 バイト数 | 1,048,576 (1 MiB) |
| サーフェスが読み込む JSON ドキュメント 1 件の生バイト数 | 67,108,864 (64 MiB) |

パラメータ数の上限は、制約の実行可能性探索を有界に保つためのものです。探索は 1 階層につき 1 パラメータを進み、充足する連鎖は 1 階層につき探索予算のノードを 1 つだけ消費します。探索の深さを制限するものは他にありません。

最後の行は、その上の 6 つとは性質が異なります。理由は後述のドキュメントガードの節で説明します。

## 呼び出し側に見えるもの

上限は生成を始める前に検査されるため、拒否のコストはかからず、当たった上限もメッセージが名指しします。

| サーフェス | 拒否の届き方 |
|---|---|
| コマンドライン | 終了コード 3。メッセージは標準エラー出力へ |
| Python | `CoverwiseError` を送出。メッセージを保持します |
| JavaScript / TypeScript | `CoverwiseError` を送出。メッセージを保持します |
| C++ | 戻り値の `error` が非 ok になり、`code` は `kInvalidInput` |

メッセージは上限と、それを超えた値を名指しします。コマンドラインでは次のように表示されます。

- `parameters exceed maximum of 1024`
- `parameter 'p0' values exceed maximum of 16384`
- `seeds exceed maximum of 100000`
- `constraints exceed maximum of 256`
- `p0[0] exceeds 65536 UTF-8 bytes` — 問題の文字列はその位置で名指しされます
- `Input strings exceed 1048576 UTF-8 bytes`

## バイト予算に計上されるもの

7 つのうち 2 つは、個数ではなくバイト数の予算です。文字列単位の上限は個々の入力文字列それぞれに適用されます。合計の上限は入力全体でひとつの予算であり、すべての文字列が読み込まれた場所で一度だけ計上されます。対象はパラメータ名と値、エイリアス、等価クラス名、制約式、サブモデルのパラメータ名、`weights` オブジェクトのキーであるパラメータ名と値名、そして `tests`・`seeds`・`existing` 配列の各行の値です。

```json
{
  "parameters": [
    { "name": "os", "values": ["Windows", "macOS", "Linux"] },
    { "name": "browser", "values": ["Chrome", "Firefox", "Safari"] }
  ],
  "constraints": ["IF os = Windows THEN browser != Safari"]
}
```

このモデルが合計予算から消費するのは 83 バイトです。1 つ目のパラメータの名前と値で 19 バイト、2 つ目で 26 バイト、制約式で 38 バイトです。ドキュメント内の他のものは計上されません。波括弧、引用符、コロン、`name`・`values`・`constraints` といったキーは JSON の構文であって、呼び出し側が渡したテキストではないからです。

行に対して計上されるのは **値** だけで、キーは計上されません。キーはパラメータ名であり、モデルの文字列としてすでに一度計上されています。行ごとに計上すると同じテキストを行数分だけ数えることになります。計上されるのは **文字列** の値だけです。数値や真偽値の行の値には費用がかかりません。

行にまったく費用がかからないのは C++ でスイートを組み立てる場合だけです。C++ の行は値名ではなく値インデックスを持ち、インデックスはテキストではないためです。同じスイートを JSON で書けば各行の文字列値はすべて計上されるので、大きなスイートがライブラリでは受理され、コマンドラインでは拒否されることがあります。この違いの詳細は[C++ API](cpp-api.md)にあります。

## 先に効く上限

多くのモデルでは、合計バイト予算のほうが行数の上限より先に効きます。100,000 行は上限であって、その規模のスイートが受理されるという約束ではありません。1 MiB を 100,000 行に分けると 1 行あたりの行テキストは約 10.5 バイトで、これに収まるのは非常に狭いモデルだけです。文字列値を 5 バイト、1 行につきパラメータごとに値 1 つとすると、2 つの上限は次の位置で交わります。

| 1 行あたりのパラメータ数 | 受理される行数 |
|--------------------|---------------|
| 2 | 100,000（行数の上限が先に効く） |
| 3 | 69,902 |
| 10 | 20,968 |
| 100 | 2,094 |

上限は両方の次元の関数なので、これらの数値はモデル自身の文字列が行に比べて小さいことを前提としています。名前が長かったり値が多かったりするモデルは同じ予算の一部を使うため、この数値は下がります。

100,000 行を大きく下回るのに拒否されるのが、不具合ではなく実際の上限である理由もこれです。メッセージは行数ではなく予算を名指しします。値の名前を短くすれば行数はそのぶん増えますし、予算に収まらないスイートは分割して分析するしかありません。

## ドキュメントガード

ドキュメントの上限は受理契約の一部ではありません。ファイルや標準入力のストリームの生バイトに対し、パースする前の到着時点で適用されるメモリガードであり、暴走したストリームや途中で切れたストリームが際限なくメモリに読み込まれるのを防ぎます。

したがってこの上限は、波括弧・引用符・コロン・繰り返されるキーといった JSON の構文も数えます。一方、合計バイト予算が数えるのは呼び出し側が渡したテキストだけです。通常の幅のモデルでは他の 6 つよりずっと外側にあるため、呼び出し側はそちらに先に当たります。幅の広いモデルでは構文が支配的になり、ドキュメントが最初に当たるのがこのガードになります。パラメータ 100 個で 100,002 行の JSON はおよそ 133 MiB ですが、行テキストは 1 MiB をはるかに下回ります。それでも `file '<path>' exceeds the maximum of 67108864 bytes` で拒否されます。このメッセージは「このファイルは読み込むには大きすぎる」という意味であって、スイートについての判断ではありません。スイート自体は上記のどの上限にも十分収まっていることがあります。

このガードが適用されるのは、ドキュメントをパースするサーフェスだけです。コマンドラインはそれに当たります。TypeScript のサーフェスは当たりません。パース済みのオブジェクトを受け取るため、制限すべきドキュメントが存在しないからです。定数が TypeScript 側にもあるのは、2 つの上限一覧を突き合わせられるようにするためだけです。Python パッケージはドキュメントを組み立ててコマンドラインバイナリに渡すため、送信する内容にガードが適用されます。
