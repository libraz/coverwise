# FAQ と制限

coverwise が判断しないこと、何をどんな理由で拒否するか、そしてリファレンスが列挙するフィールドの背後にある挙動をまとめます。ここで使う語彙は[用語集](glossary.md)で定義し、[入門](primer/index.md)で扱っています。

## 適用範囲

**coverwise はテストを実行しますか。**
実行しません。テストケースの集合を設計し、既存の集合のカバレッジを測るところまでです。ケースを実行し、アサーションを書き、結果を報告するのはテストランナーの仕事です。coverwise は行を渡し、行を読み返します。

**パラメータの意味を理解していますか。**
していません。パラメータは名前と、中身を問わない値のリストです。`os` が OS の名前であることも、`'0'` が特別な数値であることも、2 つの値が関係していることも推測しません。等価クラスや制約はそれを伝えるための手段であり、coverwise が動くのは宣言された内容に対してだけです。

**自分のシステムにペアワイズで十分かどうかを教えてくれますか。**
教えませんし、推測もしません。強度は、対象ソフトウェアに対するリスク判断です。t=2 が何を網羅し、強度を上げると何が得られるかは[強度](primer/strength.md)にあります。

## モデリング

**パラメータが 1 つのモデルが拒否されたのはなぜですか。**
既定の強度が 2 であり、パラメータが 1 つのモデルからは 2 つのパラメータを取るカバレッジ単位を作れないためです。エラーは両方の数値を挙げます（`Strength must be between 1 and parameter count: strength=2, parameters=1`）。`strength: 1` を指定してください。各パラメータの各値が少なくとも 1 回現れることを要求する設定です。

```typescript
import { Coverwise } from '@libraz/coverwise';

const cw = await Coverwise.create();

const result = cw.generate({
  parameters: [{ name: 'os', values: ['Windows', 'macOS', 'Linux'] }],
  strength: 1,
});

result.tests.length;  // 3, one row per value
```

**ASCII の大小文字だけが違う 2 つの値を同居させられないのはなぜですか。**
値の解決で ASCII の大小文字を畳み込むため、`os = WINDOWS` の指す先が一意に決まらないからです。1 つのパラメータに `Windows` と `windows` の両方を宣言したモデルは、恣意的な規則で解決されるのではなく、生成を始める前に拒否されます。

```text
error: Ambiguous value or alias 'windows' in parameter 'os'
```

同じ規則はエイリアスとパラメータ名にも及びます。非 ASCII 文字は畳み込まれないため、この制約がかかるのは ASCII の範囲だけです。

**境界値パラメータにも `values` は必要ですか。**
必要です。`type` と `range` を持つものもパラメータであり、その形として `values` は必須です。展開結果がそのまま値の集合になる場合は `values: []` と書いてください。そこに書いた値は置き換えられるのではなく、展開後の集合にマージされます。

**`when('status').lt('ok')` が値 `ok` ではなくパラメータと比較するのはなぜですか。**
`gt`・`gte`・`lt`・`lte` の文字列オペランドはパラメータ名として扱われ、クォートなしで出力されるためです。関係演算子は数値を比較するので、右側に置いて意味があるのは数値か別のパラメータです。1 つのベアのトークンとして書けない文字列は、別の規則に読めてしまうリテラル比較として出力されるのではなく、その場で拒否されます。

## カバレッジ

**ペアワイズ 100% は、システムがテストされたという意味ですか。**
違います。意味するのは、異なる 2 つのパラメータから取った値のペアがすべて少なくとも 1 行に現れることだけです。3 つの値が同時にそろって初めて出る不具合は、ペアワイズを完全に網羅したスイートの中にも残ります。さらにカバレッジは、アサーションが正しいかどうかも、モデルがシステムを表せているかどうかも何も語りません。テストデータの性質であって、テストへの評価ではありません。

**理論的な最小値よりスイートが大きいのはなぜですか。**
coverwise が最小のカバリング配列を探索せず、貪欲に構築するためです。最小解を求めるのは高くつき、待つ価値があることはまれです。ペアワイズのスイートの下限は、2 つのパラメータの定義域の積のうち最大のものです。この規則は[パフォーマンス](performance.md)に書いてあります。OS 3 種、ブラウザ 4 種、言語 3 種、テーマ 2 種のモデルではその下限が 4 × 3 = 12 で、coverwise は全組み合わせ 72 に対して 15 行を出します。正しさと速度が先にあり、最小性は近似します。

**制約で不可能になったタプルが未網羅として報告されるのはなぜですか。**
報告されません。有効な行が 1 つも持てないタプルは、不足として挙げられるのではなく必要タプル集合から外れるため、`uncovered` には現れません。OS 3 種・ブラウザ 3 種のモデルに次の制約を置いた場合です。

```
IF os = Windows THEN browser != Safari
```

`stats.totalTuples` は 9 ではなく 8 になり、`os=Windows, browser=Safari` のペアはそもそも消えます。それでも実行結果の `coverage` は 1 です。この違いは[制約と必要タプル集合](primer/constraints-and-the-universe.md)でグリッドを使って追っています。

**`maxTests` で途中打ち切りになると何が起きますか。**
上限のところで生成を止め、どこで止まったかをそのまま報告します。失敗もしませんし、黙って成功を装うこともありません。

```typescript
import { Coverwise } from '@libraz/coverwise';

const cw = await Coverwise.create();

const result = cw.generate({
  parameters: [
    { name: 'os',      values: ['Windows', 'macOS', 'Linux'] },
    { name: 'arch',    values: ['x64', 'arm64'] },
    { name: 'channel', values: ['stable', 'preview'] },
  ],
  maxTests: 4,
});

result.tests.length;    // 4
result.coverage;        // 0.75 — 12 of the 16 required pairs
result.uncoveredCount;  // 4
result.warnings;        // ['Generation stopped at maxTests (4) before reaching 100% coverage']
```

出力された行はいずれも妥当な行で、残りは `uncovered` が名指しします。CLI の終了コードは 2 です。よく似た 2 つのケースは挙動が異なります。`seeds` の行数を下回る上限は余ったシード行を落とし、そのことを `warnings` に書きます。一方、`extendTests` に渡した行数を下回る上限は拒否されます。この呼び出しは既存の行を保持すると約束しているからです。

**手書きスイートの行が数えられなかったのはなぜですか。**
パラメータモデルがその行を説明できないためです。`analyzeCoverage` は、パラメータが欠けている行や、モデルが宣言していない値を指す行をカバレッジ計算から外し、`report.invalidTests` に理由付きで挙げます（`value 'Linux' is not declared by parameter os`、`missing value for parameter browser` など）。レポート自体は作られます。CLI はそれを標準出力に書いたうえで終了コード 3 を返します。最後まで読めなかったスイートは、カバレッジの結果ではなく入力の問題だからです。

## 決定性

**同じスイートを 2 度得られますか。**
得られます。同じ妥当なモデルと同じシードからは、どのサーフェスでも同じ行が同じ順序で出ます。`seed` の既定値は 0 なので、`seed` を書かないモデルでも成り立ちます。適用範囲は[決定性](determinism.md)にあります。

**coverwise を更新しても、同じシードから同じスイートが出ますか。**
出るとは限りません。決定性が述べているのはアルゴリズムが入力の関数であることであって、アルゴリズムが固定されていることではありません。構築処理が変われば、同じく妥当な別のスイートが出ることがあります。バージョンを固定するか、生成したスイートをコミットして意図的に再生成してください。

## 設計上の判断

**カバレッジ解析がジェネレータから独立しているのはなぜですか。**
真値として信頼できるようにするためです。バリデータは独立した層です。`analyzeCoverage` はモデルから必要タプル集合を列挙し、行が持つものを数えます。ジェネレータが記録した内容は一切参照しません。だからこそ coverwise が書いたのではないスイートも、自分で生成したスイートと同じように判定できますし、生成済みスイートについてのカバレッジの主張にも意味が出ます。ジェネレータが自分の仕事を採点しても、手元の帳簿を読み上げるだけになります。

**`--version` フラグがないのはなぜですか。**
存在せず、`coverwise --version` は未知のコマンドとして扱われます。usage が標準エラーに出て終了コードは 3 です。バイナリが持つ自己記述の手段は `coverwise --help` だけで、こちらは標準出力に出力して 0 で終了します。

**`head` にパイプすると終了コード 3 になるのはなぜですか。**
読み手がパイプを閉じると標準出力への書き込みが失敗し、出力を届けられなかった実行は成功ではないからです。CLI はこれを入力不正として報告します。カバレッジの結果以外のあらゆる異常に使っているコードです。

```bash
coverwise generate input.json | head -c 200
# error: cannot write to standard output
# exit status 3
```

CLI はドキュメント全体を 1 行で書き出すため、文書の終端まで届く行数指定ではパイプは閉じません。途中まで読みたい場合は、いったんファイルにリダイレクトしてからそのファイルを読んでください。

**構成ごとの実行時間を載せていないのはなぜですか。**
このリポジトリの中に、その数値を再導出できるものがないからです。[パフォーマンス](performance.md)のタプル数と行数は再生成できます。モデルはページに載っていて、シードは `42` なので、実行すれば同じ数値が出ます。実時間の数値は、それを出したマシンの性質です。読者が自分の実行と突き合わせて確かめることはできません。必要な構成は自分のハードウェアで測ってください。
