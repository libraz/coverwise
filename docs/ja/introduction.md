# イントロダクション

## coverwise とは

coverwise は組み合わせテスト生成エンジンです。リソース上限内の正当かつ充足可能なモデルに対して、コンパクトなテストスイートを生成し、達成した t-wise カバレッジを報告します。制限的な `maxTests` を指定しない場合は、必要なすべてのタプルの網羅を試みます。有効な完全テストケースに含められないタプルは、カバレッジの対象集合から除外されます。

**ブラウザ**、**Node.js**、**ネイティブ C++**、および PyPI で配布する native CLI で動作し、JavaScript ビルドでは WebAssembly によりプラットフォーム固有の依存がゼロです。

## 課題

3つのOS、4つのブラウザ、3つの画面サイズをサポートする Web アプリを考えてみましょう。3 × 4 × 3 = **36通りの組み合わせ**です。パラメータを数個追加するだけで、数千〜数百万に膨れ上がります。

すべての組み合わせをテストするのは非現実的です。ランダムに選ぶと漏れが生じます。「代表的な」テストを手作業で選ぶのはエラーを招きやすく、保守も困難です。

## 解決策：ペアワイズテスト

研究によると、ソフトウェアバグの大部分は**2つのパラメータ**の相互作用（ペアワイズ）によって引き起こされ、全パラメータの同時作用ではありません。ペアワイズテストはこれを活用します：

| アプローチ | 4パラメータ × 3値のテスト数 |
|-----------|---------------------------|
| 全数テスト | 81テスト |
| ペアワイズ（2-wise） | 約9テスト |
| 3-wise | 約27テスト |

coverwise はコンパクトなカバリング配列を自動生成し、独立したカバレッジバリデータで結果を検証します。

## 基本概念

### パラメータと値

**パラメータ**はテスト対象システムの変動要素です。各パラメータは有限の**値**の集合を持ちます。

```json
{
  "parameters": [
    { "name": "os", "values": ["Windows", "macOS", "Linux"] },
    { "name": "browser", "values": ["Chrome", "Firefox", "Safari"] }
  ]
}
```

### 強度（Strength）

**強度** (t) は同時に考慮するパラメータの数を定義します：

- **t = 2**（ペアワイズ）：すべてのパラメータ値のペアが少なくとも1つのテストに出現
- **t = 3**（3-wise）：すべての3つ組が少なくとも1つのテストに出現
- 強度を高くすると、通常はテスト数が増え、より多くのパラメータ間の相互作用を対象にします

### 制約

実際のシステムには**制約**があります。たとえば Safari は macOS でしか動きません。coverwise は生成時にこれを強制します：

```
IF os = Windows THEN browser != Safari
```

無効な組み合わせは出力に含まれません。

### カバレッジ

**カバレッジ**はテストスイートに含まれる必要な t-wise タプルの割合です。coverwise は 100% カバレッジを目標とし、未達の場合（例：`maxTests` の制限）は、残っている必要タプルを報告します。

## 設計思想

coverwise は単なる生成ツールではなく、**テスト設計API** として構築されています：

- **JSON入力、JSON出力** — 基本的な使用にDSLの学習は不要
- **ステートレス** — `generate(input) → output`、セッション管理不要
- **分解可能** — 生成・分析・拡張の独立した関数
- **説明可能** — すべての結果にカバレッジ証明と人間が読める未カバータプルを含む
- **決定的** — ネイティブ C++、WASM、Pure TS は xoshiro128**、SplitMix32 seed、rejection sampling を共有し、同じ正当な入力とシードからエンジン間で同じsuiteを生成

## プラットフォームサポート

| プラットフォーム | 方法 |
|----------------|------|
| Node.js (≥ 18) | `npm install @libraz/coverwise` |
| ブラウザ | ESM インポート（WASMは自動ロード） |
| Python (≥ 3.10) | `pip install coverwise`（Linux x86_64 / aarch64、macOS 14 以降の Apple Silicon） |
| C++ (ネイティブ) | CMake、静的ライブラリ |
| CLI | `pip install coverwise`、release archive、またはソースビルド |

## パフォーマンス

以下のbenchmark構成は **100% t-wise カバレッジ** を達成し、
[独立native validator](../../tests/integration/generate_and_validate_test.cpp)で検証済みです。
制約付き正当モデルの完全coverageとengine間の決定性は
[WASM/Pure TS compatibility suite](../../js/compat.test.ts)で回帰テストしています。

### ペアワイズ (2-wise)

| 構成 | タプル数 | テスト数 | 理論下限 |
|------|---------|---------|---------|
| 5 × 3 均一 | 90 | 15 | 9 (OA) |
| 10 × 3 均一 | 405 | 21 | 9 (OA) |
| 13 × 3 均一 | 702 | 22 | 9 (OA) |
| 10 × 5 均一 | 1,125 | 52 | 25 |
| 15 × 4 均一 | 1,680 | 41 | 16 |
| 20 × 2 均一 | 760 | 13 | 4 |
| 20 × 5 均一 | 4,750 | 65 | 25 |
| 30 × 5 均一 | 10,875 | 74 | 25 |
| 50 × 3 均一 | 11,025 | 33 | 9 (OA) |
| 5 × 20 高カーディナリティ | 4,000 | 514 | 400 |

### 高強度

| 構成 | 強度 | タプル数 | テスト数 |
|------|------|---------|---------|
| 15 × 3 | 3-wise | 12,285 | 98 |
| 8 × 3 | 4-wise | 5,670 | 225 |

### 高強度（ストレステスト）

| 構成 | 強度 | タプル数 | テスト数 |
|------|------|---------|---------|
| 10 × 3 | 5-wise | 61,236 | 880 |
| 8 × 4 | 5-wise | 57,344 | 2,764 |
| 12 × 3 | 6-wise | 673,596 | 3,349 |
| 15 × 3 | 5-wise | 729,729 | 1,297 |
| 20 × 3 | 5-wise | 3,767,472 | 1,592 |

タプル数とテスト数は、同梱ジェネレータを `seed: 42` で実行した結果です。
[ドキュメント契約テスト](../../tests/integration/docs_contract_test.cpp)が実行のたびに再生成するため、
アルゴリズムを変更した場合は表が古びる代わりにテストが失敗します。理論下限は直交配列 (OA) 理論または
v² 下界に基づく既知の下限値です。貪欲法アルゴリズムは一般に理論最小値の 1.5〜2.5 倍のテスト数を
生成します。全engineが同じRNG algorithmを使用し、同じ正当な入力とseedから同じsuiteを生成します。

実行時間は構成ごとには掲載していません。ホスト・ランタイム・ビルドに左右されるうえ、
このリポジトリからは再現できない数値だからです。傾向としては、ペアワイズでは 2 つの
JavaScript engineはほぼ同等で、強度とタプル数が大きくなるほど WASM engineが優位になります。
所要時間が問題になる場合は、対象の構成を自分のハードウェアで計測してください。
